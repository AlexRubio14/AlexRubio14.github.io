01 | The Problem

The project started from a client-authoritative networking model where the client could directly communicate its position to the server, while the server primarily replicated that state. This created two fundamental problems: the server had limited authority over the actual game state, and synchronization became increasingly difficult to reason about as the number of networked entities grew.

NetworkMiddleware Goals:
01 — Server Authority: Move game-state authority to the server and run the simulation at a stable 100 Hz tick rate.
02 — Efficient UDP Networking: Build the networking layer around UDP while providing reliability guarantees.
03 — Efficient Replication: Reduce required bandwidth through bit-level serialization and delta compression.
04 — Engine-Agnostic Design: Keep networking concerns independent via transport abstraction ('ITransport').
05 — Testability: Enable full testing without depending on real network sockets ('MockTransport').

03 | Protocol Design & Reliability

UDP provides the low-overhead transport required by the authoritative simulation, but it does not provide delivery, ordering or acknowledgement guarantees. NetworkMiddleware implements reliability at the protocol level.

SEQUENCE
↓
ACK & ACK BITMASK (32-bit mask)
↓
TYPE & FLAGS
↓
TIMESTAMP
  • Sequence Numbers & ACK Piggybacking: Packets carry sequence information and acknowledgements are embedded directly into outgoing gameplay packets via a 32-bit bitmask, eliminating dedicated acknowledgment packets.
  • Selective Reliability: Time-sensitive state uses unreliable delivery where newer updates supersede older ones, while critical messages use guaranteed ordered delivery.

04 | State Replication & Compression

The server continuously produces authoritative state that needs to be replicated to connected clients. Sending the complete state of every entity on every tick would quickly become expensive, so the replication pipeline progressively reduces the amount of data that needs to be transmitted.

FULL STATE 360 bits / 45 bytes
↓ Bit-level serialization
COMPRESSED STATE 149 bits
↓ Delta against baseline
UNCHANGED TICK 38 bits for an unchanged tick

The key idea is to avoid retransmitting information that the client already knows. A 'baseline' is simply a saved reference point of an entity's last known state. When an entity changes, the server compares its current state against that baseline and only sends the differences. For a tick where nothing changes, the data drops to 38 bits.

Engineering Challenge — Baseline Isolation

The initial implementation stored replication baselines using only the entity as the key:

Entity → Baseline

This caused cross-talk and data interference between clients. The problem was that a baseline is not just a property of an entity; it represents the specific reference point that a particular client is using. The data model was therefore refactored to:

(Client, Entity) → Baseline

Each client now maintains an independent replication baseline for the same entity, completely resolving cross-client interference.

Spatial Hashing and Fog of War

The world is divided into a uniform spatial grid. Instead of treating every player and entity globally, the system groups them by their physical location.

This creates a direct connection between gameplay visibility and network traffic. If an enemy is hidden by the 'Fog of War' and is not relevant to a specific client, that entity can be excluded from its replicated state. This reduces unnecessary network traffic and limits the amount of world state each client needs to process.

Client State Estimation

Network latency and packet loss can cause visual stutters or delays in movement. To make movement appear smoother between received updates, the project evaluated state estimation using a 'Kalman filter' and constant-velocity models.

These techniques estimate the expected movement of an entity between network updates. The final integration of client-side prediction and server reconciliation for Unreal Engine remained outside the implemented scope of this version and was instead explored as part of the architectural design.

06 | Performance Engineering & The I/O Journey

Profiling revealed that game logic simulation was stable, while network I/O syscall overhead represented the primary bottleneck under benchmark loads.

Key Takeaway: Replacing individual 'send()' calls with Linux sendmmsg() batched syscalls via an asynchronous dispatcher reduced network I/O from 7.20 ms to 0.17 ms (-97.6%), while game logic remained at ~3.77 ms.

07 | Testing & Validation Architecture

Developed using Test-Driven Development (TDD) backed by 254 automated tests using Google Test.

MockTransport Integration:
• In-process transport implementation simulating bidirectional networking without real OS sockets.
• Deterministic test execution isolated from system network configurations.
• Reproducible network conditions (artificial packet loss and delivery delay simulation).

08 | Results, CI/CD & Scalability Limit

Automated pipelines and stress testing validated production readiness and system limits:

  • CI/CD & Deployment: GitHub Actions automated build/test pipelines, containerized via Docker and pushed to GitHub Container Registry for Azure deployment.
  • WAN Validation: Tested with 49 concurrent WAN clients with zero CRC errors observed during recorded tests.
  • Scalability Benchmark (99 clients): Stress testing reached 99 clients at 14.24 ms loop time. Because each client receives state for all entities, replication scales at $O(n^2)$, highlighting the need for dynamic relevancy sets in larger sessions beyond 5v5 MOBA scopes.
Engineering Takeaways:
• Profile before optimizing: bottlenecks reside in system call overhead rather than simulation logic.
• Model state around ownership: scope replication baselines to client/entity relationships.
• Abstract transport ('ITransport') to enable robust 'MockTransport' unit testing.
