01 | The Problem

The project started from a client-authoritative networking model where the client could directly communicate its position to the server, while the server primarily replicated that state. This created authority and synchronization issues as the number of networked entities increased.

NetworkMiddleware Goals:
Server authority with a stable 100 Hz tick rate.
Robust UDP networking with selective reliability.
Efficient replication through bit-level serialization and delta compression.
Engine-agnostic design through the 'ITransport' abstraction.
Full testability without real sockets through 'MockTransport'.

02 | Architecture & Design Decisions

The architecture separates game simulation, networking logic, protocol handling and transport. The core depends on 'ITransport' rather than concrete socket implementations, while dependencies are provided through constructor injection instead of singletons.

03 | Protocol Design & Reliability

UDP provides low overhead but does not provide delivery or ordering guarantees. NetworkMiddleware implements reliability at the protocol level using sequence numbers, 32-bit ACK bitmasks and selective reliability channels.

  • ACK Piggybacking: Acknowledgements are embedded into gameplay packets through a 32-bit bitmask.
  • Selective Reliability: Independent channels are used for unreliable ephemeral data and reliable ordered critical messages.

04 | State Replication & Compression

The replication pipeline progressively reduces the amount of state that needs to be transmitted through bit-level serialization and baseline delta compression.

FULL STATE 360 bits / 45 bytes
↓ Bit-level serialization
COMPRESSED STATE 149 bits
↓ Delta against baseline
UNCHANGED TICK 38 bits for an unchanged tick

The key idea is to avoid retransmitting information that the client already knows. A 'baseline' is a saved reference point for an entity's previously replicated state. When an entity changes, the server compares its current state against that baseline and only sends the differences. When no relevant state changes during a tick, the encoded data can be reduced to 38 bits.

Engineering Challenge — Baseline Isolation

The initial implementation stored replication baselines using only the entity as the key:

Entity → Baseline

This caused cross-talk between clients because different clients could end up sharing replication state. A baseline is not simply a property of an entity. It represents the specific reference point that a particular client is using for that entity.

The data model was therefore refactored to:

(Client, Entity) → Baseline

Each client now maintains an independent replication baseline for the same entity, isolating replication state between clients.

Spatial Hashing and Fog of War

The world is divided into a uniform spatial grid. Instead of treating every player and entity globally, the system groups them by their physical location.

This creates a direct connection between gameplay visibility and network traffic. If an enemy is hidden by the 'Fog of War' and is not relevant to a specific client, that entity can be excluded from its replicated state. This reduces unnecessary network traffic and limits the amount of world state each client needs to process.

Client State Estimation

Network latency and packet loss can cause visual stutters or delays in movement. To make movement appear smoother between received updates, the project evaluated state estimation using a 'Kalman filter' and constant-velocity models.

These techniques estimate the expected movement of an entity between network updates. The final integration of client-side prediction and server reconciliation for Unreal Engine remained outside the implemented scope of this version and was instead explored as part of the architectural design.

06 | Performance Engineering & I/O Optimization

Profiling showed that simulation logic was stable, while network I/O system call overhead was the primary bottleneck.

07 | Testing & Validation Architecture

Test-driven development (TDD) backed by 254 automated tests using Google Test and 'MockTransport' to test networking behaviour without real sockets.

MockTransport Integration:
• In-process transport implementation for bidirectional networking without real OS sockets.
• Deterministic test execution isolated from system network configurations.
• Reproducible network conditions, including artificial packet loss and delivery delays.

08 | Results, CI/CD & Scalability

The project was validated beyond isolated tests through automated CI/CD pipelines, containerized deployment and WAN/scalability testing.

  • CI/CD & Deployment: Automated build and test pipelines using GitHub Actions, Docker, GHCR and Azure infrastructure.
  • WAN Validation: Tested with 49 concurrent WAN clients, with zero CRC errors observed during the recorded tests.
  • Scalability Limit: The benchmark reached 99 clients at 14.24 ms. The replication model scales at O(n²), highlighting the need for dynamic relevancy sets as a future direction.
Engineering Takeaways:
• Profile before optimizing: the main bottleneck was syscall overhead in network I/O.
• Model state around ownership: replication baselines must be isolated per client and entity.
• Abstract transport through 'ITransport' to enable robust 'MockTransport' testing.
