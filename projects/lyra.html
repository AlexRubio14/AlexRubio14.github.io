02 | Character Architecture

The problem: as interactions grew, movement, companion actions and gameplay states started to depend on each other through boolean flags. I wanted each state to own its behaviour instead of the character controller deciding everything through an ever-growing list of conditions.

The solution: a flat, data-driven finite state machine. Every state follows the same interface and controls its own lifecycle, and the state configuration lives in a Data Asset instead of being hard-coded.

From the editor

Design patterns used

  • State BPC_StateMachine + one BP_State* per state
  • Observer The active state reacts when the Animation Blueprint fires OnThrowStarted and OnThrowCompleted instead of checking every frame
  • Mediator Holding, Aiming and Throwing never talk to each other or to the dragons directly. Everything goes through BPC_DragonHandler
  • Strategy DA_LyraStateConfiguration maps each state to its class, so BPC_StateMachine never references a concrete state

Performance: each state is created the first time it is needed and then cached in a TMap , and Tick only runs where it is required. Lyra held a stable 60 FPS with zero crashes on the documented target hardware.

Why Blueprints and not C++? Nobody on the team had solid Unreal experience, so we kept the whole project in Blueprints to let designers and artists read and tweak logic. The architecture rules above (single responsibility, interfaces, data-driven configuration) were how I kept a visual codebase maintainable.

In the game

Input by context: instead of keeping every action permanently bound, Input Mapping Contexts are layered by meaning (for example IMC_LyraDragonActions ) and swapped by the state machine, so each state only exposes the inputs that make sense.

Attachment & Animation: When a dragon is picked up, its attachment to the character's skeletal mesh is synchronized with animation events. Sockets provide the attachment point, while animation notifies coordinate the moment when the gameplay state changes.

04 | Camera-Relative Movement

Lyra uses fixed cameras placed along rails, with smooth transitions between viewpoints. During a camera transition, world-space movement can make the player's controls feel inconsistent with what the player sees.

Solution: movement input is calculated relative to the active camera (Camera Forward) instead of directly using absolute world-space directions, so input direction stays intuitive while the camera changes.

05 | Debugging

Two bugs I ran into during development and how I tracked them down.

Invisible subtitles in cinematics

Symptom
The subtitle widget never appeared while a Level Sequence played; everything fired at once when it ended.
Ruled out
Widget ZOrder, Cinematic Mode, OnCameraCut.
Root cause
The Event Track's Fire Mode was misconfigured, so the Director Blueprint did nothing during playback.
Fix
Correct Fire Mode on the Event Track: subtitles fire in sync.

UI manager race condition

Symptom
"Accessed None" errors and broken fades when the player entered and left a trigger quickly.
Root cause
RemoveFromParent on a reference that was no longer valid, plus overlapping fade logic.
Fix
IsValid guards, state reduced to two references (CurrentWidget, WidgetToHide) and one Timeline driven with PlayFromStart / ReverseFromEnd.

06 | Production

A team of seven (programming, design, art and animation) building a vertical slice in one academic year. As producer I planned the sprints and organised how the team worked day to day.

  • 16 sprints (Scrumban)
  • 940 changelists in Perforce
  • 8 playtesting sessions
  • Scrumban: weekly sprints, milestone tracking and cross-discipline coordination in Jira and Confluence. I used the Cumulative Flow Diagram and the velocity chart to spot bottlenecks and reassign capacity.
  • Perforce Helix Core: I designed the repository policy: the depot setup, exclusive checkout for .uasset files so two people never edit the same binary, and a simpler stream layout.
  • Nightly builds: Marc Climent built the Jenkins pipeline. As producer I defined which pipelines the team needed, wrote some of them and helped set up the build machine. Every night it compiled, cooked and packaged the game, so a broken build was caught within a day.
  • Marketing: development content on social media: 8,686 views on TikTok across 9 videos and 7,718 on Instagram.

What I learned

Designing the state machine made me think about which system owns each piece of behaviour. Being producer at the same time made me care about something else: designers and artists had to be able to read and change what I built, too.

Next time I'd check that a tool can actually give me the metrics I need before relying on it.
