01 | The Problem

The starting point was AA4, a 2D shooter I made in 2023 where the client told the server its own position and the server simply passed it on. That made teleport cheats trivial and players drifted out of sync. NetworkMiddleware fixes it from the architecture up.

Before · AA4 (2023)

The client decides

  • The client sends its position and the server trusts it
  • No fixed tick rate
  • Any client can teleport
After · NetworkMiddleware

The server decides

  • The client only sends its intention: a 24-bit input
  • The server simulates the world 100 times per second
  • Positions come only from the server, clamped to the map

Why not use an engine's networking? Unreal's replication, Mirror or Photon work as black boxes tied to their engine. A competitive MOBA needs many lightweight Linux servers, and control over every bit on the wire, so I wrote the middleware with no engine dependency. The plan is for Unreal to be only the client that draws the game.

02 | Architecture

Two rules shape every decision: modules only know each other through interfaces, and there are no singletons. The project is split into CMake libraries, and only the executable creates concrete objects and wires them together.

Design patterns used

  • Adapter SFMLTransport is the only class that knows SFML exists. Everything above it moves raw bytes through ITransport
  • Factory TransportFactory::Create(TransportType) : adding a new transport needs no change in Core or in main
  • Dependency Injection NetworkManager receives an ITransport& in its constructor. In the tests that reference is a MockTransport
  • Callbacks (IoC) The network layer exposes events as std::function , so the Job System could be placed between network and game logic without touching network code

The payoff: when the SFML sockets became the bottleneck, I swapped in a new POSIX transport with zero changes in Core.

03 | The UDP Protocol

TCP is reliable, but one lost packet blocks everything behind it: a lost chat message would freeze every hero's position. UDP never waits, but it guarantees nothing, so the protocol adds its own guarantees on top. Every packet starts with the same 104-bit header:

ACKs for free: ack_bits confirms the 32 packets before ack , one bit each. Every packet a side sends confirms what it has received, so the protocol never sends a packet just to say "got it". Sequence wrap-around (65535 to 0) is handled with signed 16-bit arithmetic, without special cases.

Three channels, one socket

  • Unreliable Snapshots, inputs, heartbeats. If one is lost, the next tick replaces it.
  • Reliable Ordered Purchases, abilities, level-ups. Exactly once and in order.
  • Reliable Unordered Deaths and chat. Exactly once, order does not matter.

Reliable packets are resent at max(30 ms, RTT × 1.5) , with the RTT smoothed by an exponential moving average. Resending fast on a slow connection would only add congestion. Each resend rebuilds the header with fresh ACKs, so retransmissions also report what has arrived.

Connection handshake

  1. 1 Request
  2. 2 Challenge
  3. 3 Response
  4. 4 Accepted

The server answers a connection request with a random 64-bit salt, and the client has to send it back. A client can only know the salt if it really receives packets at that IP and port, which stops address spoofing. The accepted packet carries a reconnection token: for 120 seconds a dropped client can come back, even from another network, and find its session intact.

04 | Replication & Compression

Every tick the server has to tell each client what changed. Sending the C++ struct as it is would cost 360 bits per hero, so every field is written with only the bits it needs, and then only the fields that changed are sent.

RAW STRUCT 360 bits
↓ bit-level serialization (−59%)
FULL HERO STATE 149 bits
↓ delta against the confirmed baseline (−74%)
NOTHING CHANGED 38 bits
  • Quantization Positions use 16 bits instead of a 32-bit float. On a 1000 × 1000 map the error is at most 1.53 cm, invisible for characters tens of units tall.
  • Baselines The delta is computed against the last state the client confirmed through ack_bits , never against the last one sent. If a packet is lost, the next delta still starts from what the client really has.
  • ZigZag (n << 1) ^ (n >> 31) turns small negative deltas into small unsigned numbers, so they also fit in a few bits.
  • BitWriter Writes in 32-bit blocks instead of bit by bit: at most 5 iterations per value instead of 32. I chose it over Protocol Buffers and FlatBuffers to keep control of every bit.

05 | The 100 Hz Tick

The server has 10 ms per tick. In that time it reads every packet, applies the inputs, simulates the world and prepares, for each client, only what its team can see.

  1. manager.Update() read every waiting packet: handshakes, ACKs, inputs
  2. ForEachEstablished apply each input, clamped; predict it with Kalman if it was lost
  3. gameWorld.Tick(dt) authoritative simulation, and a copy of the state for lag compensation
  4. spatialGrid.MarkVision() recompute what each team can see
  5. SerializeSnapshotFor() every third tick: serialize per client in parallel, then send
  6. ++tickID the client will use it to reconcile its prediction

A one-word fix: the receive step used if and read one packet per tick. With 48 bots that is about 29 packets per tick, so 28 piled up in the kernel buffer and latency kept growing. Changing it to while , the standard pattern in authoritative servers, fixed it.

What the server adds on top

Fog of war

A 20 × 20 grid stored as std::bitset<400> per team, 50 bytes. Asking if a cell is visible is O(1), and hidden enemies are never sent.

[ x, y, vx, vy ]

Kalman prediction

When a client's input is lost, the server predicts its movement with a constant-velocity filter and corrects it silently when the real input arrives. No change on the wire.

Lag compensation

32 past states per entity (320 ms). A hit is checked against the world as the shooter saw it, using the tick ID in their input.

06 | Debugging

Two bugs that taught me the most, and the limit the real internet exposed.

Zero connections

Symptom
The first headless bots in Docker never connected to the server.
Ruled out
The socket was open ( ss -ulnp ) and packets did arrive ( nc -u ).
Root cause
ParseIpv4 built the address in little-endian, but SFML expects network byte order: 127.0.0.1 became 1.0.0.127 .
Fix
Build the address in big-endian. Found in minutes by ruling out one layer at a time.

Delta compression that wasn't

Symptom
With 46 bots and every hero moving, delta efficiency fell to 0% and the loop took 39.5 ms, four times the budget.
Root cause
The history assumed one entity per sequence number, so only the last entity of each tick used delta. On top of that, 2,116 send() calls per tick.
Fix
Baselines keyed by (client, entity) and one packet per client per tick: 1.62 ms and 74% efficiency.

The real internet: over budget

Tested from Spain against Azure with 49 bots, the protocol held up: 0 retransmissions and 0 CRC errors in 60 seconds. The server did not: the full loop took 10.97 ms, over the 10 ms budget, while reading packets took only 3.77 ms of it.

Reading packets 3.77 ms
Full loop 10.97 ms
10 ms budget

Fix, in three steps: a new transport with Linux sendmmsg() that sends every client's packet in one system call instead of 49; an AsyncSendDispatcher on its own std::jthread so the game loop never waits for that call; and snapshots every third tick (about 33 Hz) while the simulation stays at 100 Hz.

After the fix I only re-ran the WAN test with 10 bots: a 0.17 ms full loop and 19.7 kbps per client. Repeating it with 49 is the next measurement I owe this project.

The known limit: with 99 clients over WAN the tick reached 14.24 ms and kept growing. Every client receives every entity, so the cost is O(n²). It is outside the 5v5 scope the system was designed for, but it tells me exactly what to build next.

What I learned

The hardest part was not making packets travel, it was deciding who owns each piece of state. The delta bug only went away when baselines belonged to a (client, entity) pair. Building the tests first also paid off: when the full benchmark exposed two silent bugs, 157 existing tests made the fixes safe.

Measure before optimizing, and know exactly what each metric measures before quoting it.

What I would build next

  • Relevancy sets: each client gets only nearby or visible entities, from O(n²) to O(n × k).
  • Client-side prediction: the client moves instantly and reconciles with the server using the tick ID.
  • Unreal bridge: networking on its own thread inside an ActorComponent.
  • Encryption: DTLS or ChaCha20 on top of the transport.
